# Security policy

This is a prerelease, single-user developer workspace. Codex can execute commands and edit files with the operating-system user's privileges. It is not a multi-tenant sandbox.

## Reporting

Use [GitHub private vulnerability reporting](https://github.com/danvilig/codex-remote-web/security/advisories/new) for this project. The repository setting has been enabled and verified through the GitHub API. Sign in to GitHub to submit a private report. Do not publish exploit details in issues or send independent-project reports to the reference project. See the [release process](docs/RELEASING.md) for maintainer verification steps.

## Access boundaries

- The default listener is `127.0.0.1:8899`; do not expose it directly to the Internet.
- Local mode retains loopback development access and optional LAN password/token compatibility. First-run password setup is only suitable for a trusted LAN.
- Cloudflare mode requires a valid application JWT and the configured single identity on HTTP, SSE and both WebSocket entrypoints. Loopback, passwords and Basic/Bearer tokens do not bypass it.
- Access authentication does not change Codex command approval, sandbox configuration or Linux permissions. File downloads, native config changes and browser RPCs retain their existing allowlists.
- Live connection expiry is enforced by this application. Access revocation is not claimed to terminate established sockets immediately; see the deployment guide for connection limits and validation.
- Browser disconnects do not stop Codex tasks while the gateway remains alive. UUID-bound receipts and a persistent queue coordinate submissions from this application; uncertain submissions are not automatically replayed and queues pause after a gateway restart. This does not guarantee native exactly-once execution or restore model tasks after the App Server exits.
- Independent PTY and review writes require explicit server-side capability switches and remain disabled by default.

Raw Access JWTs, credentials, private prompts and full protocol payloads must not be logged by authentication code or placed in a release artifact. Historical environment notes and extracted resources are excluded from public source snapshots and release packages. This is an independently redesigned project whose primary security boundary is Cloudflare Tunnel + Access; the private development repository retains its history, while public snapshots start with an independent initial commit and retain only the necessary reference-project/development provenance. Removing a resource from a development commit does not erase earlier history.

## Manual project file editing

Files can directly edit existing UTF-8 project text files up to 256 KiB. This is an authenticated manual workspace operation, independent of model approval profiles and the separate Review write capability. GET/POST `/api/files/document` limits access to a specified project within the existing browse roots; additional download-only roots do not grant write access. Saves require same-origin JSON and the workspace request header. Protected credential paths, symbolic-link components, non-regular files and multiply linked files are rejected. Read-only files stay read-only. Content revisions prevent detected stale overwrites, and a same-directory temporary file is synced and renamed to avoid partial contents. Checks and replacement are synchronous within one gateway; external OS processes do not participate in a file lock, so this is not a guarantee against an external modification after the final check. Ordinary permission bits are preserved; the editor does not preserve extended attributes/ACLs. Files needing that metadata should be edited with the appropriate system tools.

Unsaved text stays in current-page memory and is never sent to Codex merely by editing. Save failures retain drafts. Reload/discard is explicit, and navigating away while dirty requests the browser's unsaved-change warning; recovery after a browser/process crash is not promised. Markdown block editing operates on source ranges and uses the same HTML sanitizer as other document rendering. Browser clients should be fully trusted, as they can already submit workspace tasks.

## Local deployment setup

`GET /api/remote-access/status` is an authenticated, read-only workspace endpoint. It returns an explicit allowlist of public origin, authentication mode, allowed email, Team Domain and current verified session identity/expiry. The production gateway uses its active Access configuration; local workspaces may read the completed deployment receipt for these fields. It never returns the receipt, AUD, probe nonce, service environment or tokens and grants no setup privileges. Status read failures are shown separately from an unconfigured workspace.

The `/api/setup/` control plane and standalone setup page are loopback-only, reject public Host/Origin and proxy headers, and use a single-use bootstrap credential, HttpOnly SameSite session and per-session CSRF proof. They do not grant access to model, terminal or project RPCs. The readiness probe additionally requires a deployment-specific private nonce. Access JWT requirements on workspace endpoints remain unchanged.

After successful validation, Cloudflare management tokens are persisted in `~/.config/codex-remote-web/management-token.json`, with owner-only directory/file permissions (700/600). This is a plaintext owner credential protected by filesystem permissions, not an encrypted vault. Reads reject symlinks, non-regular files, oversized files and permissive or foreign-owned files. Tokens never appear in browser storage, API responses, logs, deployment receipts or native service environment files. Local management sessions restore the saved credential; locking drops the in-memory client, while deleting the saved token removes the file and the current client without revoking the Cloudflare token or deleting the deployment. Other already-open management processes can retain their in-memory client until locked or expired. A successful deployment leaves a private receipt for diagnostics and cleanup. Setup credentials and the receipt must not be published. The wizard reuses an existing Tunnel and changes only its managed route; the provider replaces the entire Tunnel configuration and does not provide a multi-resource transaction. Concurrent external edits may require manual reconciliation.

New Tunnel provisioning creates a separate user connector service, preserving existing cloudflared units. Its runtime Tunnel token is persisted only in a mode-600 private file; this is distinct from the saved management API token. Local identity detection matches connector UUIDs from the active systemd invocation to provider metadata, never using tokens or public IP inference. An unconfirmed existing connector requires explicit user confirmation; matched local connectors mixed with unknown replicas are rejected for this loopback-only origin.


Configuration changes require an explicit read-only preview and apply action in a local management session. Supported changes stay in the current Cloudflare account: hostname/zone, an existing local Tunnel, service port and allowed email. Preview and apply verify resource ownership, service files and the provider snapshot; new ports must be available. The service environment is patched only for the selected Access/address settings, preserving the unit, unrelated environment and probe nonce. Changing hostname creates a new single-identity Access application before enabling its protected route/DNS. Changing a Tunnel for the same hostname patches only the existing CNAME target. The original dedicated connector's provenance remains independent of the selected Tunnel.

A private journal records the old and candidate configurations and mutation intents before writes, including uncertain provider responses. Before commit, recovery rolls back owned changes; after the candidate has been verified and committed, recovery finishes removing the old owned resources. Explicit recovery is available across process restarts. Concurrent manual edits stop automatic recovery; whole-deployment deletion is never a fallback. Cloudflare does not provide atomic transactions or conditional Tunnel configuration replacement: external concurrent edits may need manual reconciliation, and updates can temporarily deny public access. The separate local management entry remains available.

## Temporary access without a domain

Protected Quick Tunnels delegate email OTP and allowlist enforcement to cloudflared's `--allowed-mail` authorizer. This mode is separate from the self-hosted Access JWT mode: the application does not treat forwarded email/JWT headers as proof. A dedicated HTTP listener is reachable only through a Unix socket inside a private random mode-700 directory. It is activated only after the supervised connector reports protected mode, a validated `https://*.trycloudflare.com` hostname, and an established tunnel connection. Every request also pins Host/Origin; setup routes are absent. The regular TCP listener retains its original authentication and never uses this trust path. Processes running as the same OS user already control Codex and can access this socket; OS account isolation remains a requirement.

The connector receives only a filtered environment, private Unix ingress config, one exact email, and the private socket path; inherited `TUNNEL_*`, Codex credentials and Access environment are not forwarded. Raw connector output is consumed in a separate Node supervisor and is not returned to the browser or persisted. The process-local status contains only state, email and assigned URL. A private lock prevents concurrent management by another process. No public cloud resource, deployment receipt or systemd service is modified. There is no automatic unprotected fallback.

Starting/stopping requires the same loopback Host/Origin, HttpOnly setup session and CSRF proof as permanent setup. Status polling does not replay a start. Leaving the page or locking local management does not stop the connection; explicit stop and WebUI shutdown close its listener, active WebSockets and PTYs. A supervisor watches the owner's IPC pipe and terminates the child even after abrupt owner exit. Connections re-handshake at least every five minutes; this does not promise instantaneous expiry/revocation of cloudflared's process-local email session. SSE is disabled; failed WS reconnects preserve drafts and do not resubmit execution. Only public hostname data is encoded in a local SVG QR; no third-party QR service receives addresses.

## Scheduled execution and customization

Enabling a schedule authorizes future model and tool execution while the gateway remains online, even when all browser tabs are closed. Tasks use native on-request approvals and bounded read-only/workspace-write profiles. The scheduler stores private task prompts and paths under CODEX_HOME/remote-web-scheduler with owner-only permissions. Restart, disconnect and uncertain dispatch pause affected tasks without replay. A file lock coordinates local gateways only, not independent hosts or PID namespaces.

Customization mutations require authenticated same-origin JSON requests, a workspace header and explicit confirmation. Plugin identities are resolved again from the native catalog; client-supplied plugin paths/config keys are never accepted. Local skill copies are bounded and exclude links and credentials; installation executes no script. Installed instructions can subsequently guide Codex, so install only trusted resources. Built-in and plugin-owned skills cannot be deleted through the user-skill interface.

Uploaded attachments are private workspace data under `CODEX_HOME/remote-web-attachments` (700/600). Uploads require the existing authenticated identity plus same-origin typed requests and an explicit workspace header. Opaque IDs resolve only within the selected project for model submission; symlink storage, foreign ownership and permissive file modes are rejected. General private-path download restrictions remain unchanged. HTML/SVG are forced downloads; only recognized raster image formats may render inline under a sandbox CSP. Uploading does not authorize model execution; sending follows the selected Codex permission profile. Removing a draft chip does not delete the stored file; previewed cleanup can remove only old unbound uploads that are not referenced by the persistent queue. Binding/upload and cleanup share a cross-gateway storage lock, and execution revalidates candidates. Native sessions, credentials, memories and project files are never cleanup targets. Do not include private attachment storage in release artifacts.
